## Что реально ограничивает FPS и грузит сеть сейчас

    **1. `chunk_size = 60000` — это главная проблема.** UDP-датаграмма такого размера не влезает в Ethernet MTU (1500 байт) и фрагментируется IP-стеком на ~40 фрагментов. Если теряется **один** IP-фрагмент — теряется весь чанк 60000 байт, а значит теряется **весь кадр** (в `receive_screen` кадр собирается только при `len(frame) == total_chunks`). На реальной Wi-Fi/загруженной сети это резко увеличивает процент "выброшенных" кадров и заставляет тратить трафик впустую.

    → Уменьшить `chunk_size` до ~1400 байт (с учётом 16-байтного заголовка и UDP/IP overhead), чтобы каждый чанк укладывался в один Ethernet-кадр без фрагментации.

    **2. Кадр всегда отправляется целиком, даже если экран не менялся.** Статичный экран (текст, презентация, ожидание) всё равно гонит полный JPEG каждые 100 мс — это чистый расход полосы без пользы.

    → Перед отправкой сравнивать хэш/чек-сумму нового скриншота с предыдущим (можно по уменьшенной копии для скорости) и, если не изменилось, не слать кадр вообще (или слать редкие keep-alive).

    **3. `time.sleep(0.10)` — фиксированная пауза без учёта времени захвата+кодирования.** Реальный интервал между кадрами = время grab+JPEG+sendto + 0.10 сек, то есть FPS всегда ниже теоретических 10.

    → Считать время, потраченное на обработку кадра, и спать `max(0, target_interval - elapsed)`.

    **4. `ImageGrab.grab()` из PIL — медленный способ захвата экрана на Windows**, особенно на больших областях. Библиотека `mss` захватывает через DXGI/BitBlt и обычно в 3–5 раз быстрее для повторяющихся снимков одной области.

    **5. Broadcast (`255.255.255.255`) грузит вообще все устройства сети**, включая те, что трансляцию не смотрят — свитч разошлёт широковещательный трафик на все порты, и каждая машина в сегменте вынуждена обрабатывать пакет на уровне драйвера, даже если сбрасывает его. Если получателей немного и они известны — юникаст на список IP снижает нагрузку на сеть в целом на порядок. Если нужен именно "многим сразу" сценарий — IP-multicast с IGMP даёт эффект broadcast, но трафик реально идёт только туда, где есть подписчики.

    **6. JPEG quality=75 без адаптации** — можно снижать качество/разрешение динамически при обнаружении потерь пакетов или роста времени кадра, и повышать обратно, когда сеть "отдыхает".

    ## Конкретные правки в `broadcast_screen`

    ```python
    import hashlib
    from PIL import Image

    def broadcast_screen(self):
        frame_id = 0
        target_interval = 1 / 15  # целевой FPS, вместо жёсткого sleep
        prev_hash = None
        chunk_size = 1400  # укладывается в Ethernet MTU без IP-фрагментации

        try:
            while self.broadcasting:
                t0 = time.perf_counter()

                screenshot = ImageGrab.grab(bbox=self.region)

                # быстрая проверка "изменилось ли изображение"
                # уменьшаем для скорости сравнения
                small = screenshot.resize((64, 36))
                cur_hash = hashlib.md5(small.tobytes()).digest()

                if cur_hash != prev_hash:
                    prev_hash = cur_hash

                    img_buffer = io.BytesIO()
                    screenshot.save(img_buffer, format='JPEG', quality=75)
                    img_data = img_buffer.getvalue()

                    total_chunks = (len(img_data) + chunk_size - 1) // chunk_size
                    for i in range(total_chunks):
                        if not self.broadcasting:
                            break
                        start = i * chunk_size
                        end = min(start + chunk_size, len(img_data))
                        chunk = img_data[start:end]
                        header = struct.pack('!IIII', frame_id, i, total_chunks, len(chunk))
                        self.sock.sendto(header + chunk, (self.broadcast_ip, self.udp_port))

                    frame_id += 1

                elapsed = time.perf_counter() - t0
                time.sleep(max(0, target_interval - elapsed))
        except Exception as e:
            self.status.config(text=f" Ошибка передачи: {e}", fg="red")
            self.broadcasting = False
    ```

    Что это даёт:
    - пропуск неизменных кадров экономит трафик радикально при статичном экране (частый сценарий);
    - маленькие чанки убирают "каскадную" потерю целого кадра из-за одного потерянного IP-фрагмента;
    - динамический sleep выравнивает реальный FPS ближе к целевому вместо "0.10 сек + сколько уж получится".

    ## Что ещё можно сделать при желании копнуть глубже

    - Установить `mss` (`pip install mss`) вместо `ImageGrab` — заметный прирост скорости захвата, особенно на больших областях.
    - Перейти с broadcast на multicast или список известных получателей (unicast) — самое сильное снижение нагрузки на сеть в целом, если получателей немного.
    - Адаптивное качество JPEG в зависимости от измеренного размера кадра/времени обработки (простой P-регулятор: если кадр стабильно > X КБ или обработка занимает > interval — снижать quality/scale, и наоборот).
    - В приёмнике (`receive_screen`) стоит защититься от "зависших" неполных фреймов — сейчас частично собранные `frame_id` могут годами копиться в `self.frames`, если чанк потерян и `frame_id` больше никогда не совпадёт по условию `len(frame) == total_chunks`. Ограничение "не более 10 фреймов" спасает от разрастания, но лучше явно чистить фреймы старше N кадров по времени, а не только по количеству.

    можно ли получить дополнительный выигрыш по скорости, передавая каждую секунду полный кадр, а затем только его изменения
ответ:
    Да, это классический приём из видеокодеков (I-frame/P-frame) и он даст ощутимый выигрыш — при обычной работе (курсор, набор текста, скролл) меняется обычно небольшая часть экрана, и передавать каждый раз весь кадр избыточно. Реализую так:

    Раз в секунду — полный кадр (keyframe), как сейчас.
    Между keyframe — считаем bounding-box изменившейся области (по уменьшенной копии, чтобы не тормозить), вырезаем только её, кодируем в JPEG отдельно и шлём с координатами.
    Если ничего не изменилось — вообще ничего не отправляем.
    Если изменилось слишком много (> ~50% площади) — сразу шлём полный кадр вместо region, т.к. для больших изменений он эффективнее по сжатию, и заодно это работает как защита от "рассинхрона" при резкой смене сцены (открыли видео на весь экран и т.п.).
    Приёмник держит "холст" (canvas) — полный кадр по keyframe, а delta просто вставляет (paste) в нужные координаты.
